# AEGIS — User Personas

작성일: 2026-09-07 | 단계: INCEPTION → User Stories (Part 2) | 출처: `requirements/requirements.md` v4.0 §2.1
승인된 방법론: Unit 중심 + 페르소나 태그 (Q1=A). 이 문서의 페르소나는 `stories.md`의 스토리에 태그로 연결된다.

AEGIS는 3개 신뢰 경계(웹 확인·에이전트 실행·LLM 요청)를 통제하는 단일 장비·단일 사용자 보안 워크스페이스다. 페르소나는 §2.1의 세 사용자 유형을 그대로 채택한다(C-AIDLC-1). 별도 계정·RBAC·멀티테넌트는 범위 밖(§3 제외).

---

## P-A. 주 사용자 — 개발자 (Primary Developer)

| 속성 | 내용 |
|---|---|
| **역할** | 외부 자료를 읽고 AI 코딩 도구(로컬 에이전트·클라우드 LLM)를 일상적으로 사용하는 개발자 |
| **보안 전문성** | 보안 전문가가 **아님**. 위협 모델·암호학 세부는 몰라도 됨 |
| **주요 목표** | ① 출처 불명 링크를 로컬 위험 없이 읽기 ② 검증된 제한 안에서 에이전트에 작업 위임 ③ 프롬프트에 섞인 키가 외부로 나가지 않게 하기 |
| **동기** | 생산성을 유지하면서 실수로 인한 로컬 스크립트 실행·비밀 유출·정책 약화를 피하고 싶음 |
| **좌절점(Pain)** | "왜 막혔는지" 모르는 차단, 우회 유혹, 도구마다 다른 로그로 원인 추적 곤란(P-4) |
| **성공 기준** | 차단 시 **한글 사유 + event_id + 다음 행동**을 이해하고 스스로 복구. 안전한 우회 버튼('로컬에서 계속')이 없어도 작업 흐름을 이어감 |
| **핵심 요구** | 비전문가 이해 가능한 UX(§6), 색상만이 아닌 텍스트 경고, fail-closed 시 명확한 안내 |
| **관련 스토리** | US-1(웹 격리), US-2(에이전트), US-3(시크릿 차단), US-4(상태·사유 확인) |

## P-B. 정책 관리자 (Policy Administrator)

| 속성 | 내용 |
|---|---|
| **역할** | 같은 장비를 관리하는 개발자 또는 팀 담당자. 설정 파일 수정·서명·키 교체·실행 환경 준비 수행 |
| **보안 전문성** | 중~상. 오프라인 서명 도구·ML-DSA-65 개념·신뢰키 관리 이해 |
| **주요 목표** | 정책과 검증 키를 안전하게 교체하고 재서명된 정책·신규 신뢰키로 안전하게 재시작 |
| **동기** | 정책 무결성 보장(변조·미신뢰 키 거부), 폐기 키로는 시작 불가하도록 운영 |
| **좌절점(Pain)** | 실행 중 정책이 몰래 바뀌거나(TOCTOU), 서명 옆 임의 공개키가 자동 신뢰되는 위험 |
| **성공 기준** | 재서명·키 교체 후 정상 재시작, 폐기 키·무효 설정으로는 **기동 거부**. 정책 적용 확인 전에는 '보호 활성'으로 표시되지 않음 |
| **핵심 요구** | 별도 계정·RBAC 없음(§2.1), 공개키만 실행 환경에 배포(개인키 미배포), 수동 교체·폐기 지원 |
| **관련 스토리** | US-5(정책·키 교체·안전 재시작), US-2/US-3의 정책 검증 경로 간접 관여 |

## P-C. 검증 사용자 — 동료 (Verifier / Reviewer)

| 속성 | 내용 |
|---|---|
| **역할** | README만 보고 환경을 시작해 정상·공격·장애 시나리오를 재현하는 동료 |
| **보안 전문성** | 중. 시나리오 재현·결과 파일 확인이 주 업무 |
| **주요 목표** | 숨은 수작업·실제 악성 사이트 없이 D-1~D-3와 장애 테스트를 반복 재현 |
| **동기** | 제품의 보안 주장(격리·차단·검증)이 실제로 성립하는지 독립 확인 |
| **좌절점(Pain)** | 문서에 없는 수작업, 재현 시 이전 실행과 이벤트·카운터가 섞임, mock으로 대체된 가짜 검증 |
| **성공 기준** | 사전 준비→기동→3 시나리오→장애 복구→정리를 수행하고 workflow_id로 결과 파일을 찾음. 재실행이 이전 결과와 섞이지 않음 |
| **핵심 요구** | 자체 호스팅 무해 fixture, 합성 시크릿(`SYNTHETIC / NEVER VALID`), 실제 판정·ML-DSA·OpenShell·RBI를 mock으로 대체하지 않음(§8.1) |
| **관련 스토리** | US-6(README 재현), US-1~US-5의 검증 경로 전반 |
